## 1. Overview

### 1.1 Problem Statement
Big, popular Nigerian landmarks are difficult and expensive to reach due to security issues and the cost of domestic flights. The average Nigerian earns ₦77k/month, which is not enough for local flights. Meanwhile, many beautiful, inexpensive spots go undiscovered because:
- There is no trusted source of **safety information** for these spots
- There is no **cost transparency** (entry, transport, food)
- Existing tools (Google Maps, TripAdvisor) are built for global markets, not Nigerian realities
- Information about smaller spots is scattered, outdated, or nonexistent

### 1.2 Solution (v1)
A safety-first, budget-conscious discovery platform that:
- Curates smaller, affordable, accessible spots and gives them visibility
- Uses a **color-coded safety system** (🟢 green / 🟡 yellow / 🔴 red) derived from **community reports only** in v1
- Provides **cost estimates** (entry, transport, food) for every spot
- Is built **mobile-first** for Nigerian network and device realities
- Integrates into **daily life** (commute safety, weekend planning, hangout planning), not just occasional tourism
- Lets users **save spots and plan visits** (`saved_spots` with `planned_date` and `notes`)
- Supports **booking handoffs** to external vendors (`booking_url`, `whatsapp_contact`) where a spot is bookable

### 1.3 Positioning Statement
> "The safety-first, budget-conscious discovery platform for everyday Nigerians."

Not "Google Maps for tourism." Not "TripAdvisor for Nigeria." A **lifestyle guide** for discovering, planning, and safely enjoying experiences within budget.

### 1.4 Target Audience
| Segment | Priority | Notes |
|---|---|---|
| Average Nigerians (indigenes, families, local explorers) | Primary | Core user base |
| Students and young professionals | Primary | High engagement, budget-conscious, social evangelists |
| Foreign backpackers | Secondary | Low-budget, safety-conscious |
| Luxury travelers | Secondary | Later phase |

### 1.5 Success Metrics
- Beta users who open the app more than twice in 2 weeks: **≥ 40%**
- Spots documented at launch: **100–200** (≥ 50 fully verified)
- States covered at launch: **≥ 3** (Lagos, Ogun, Abuja/Rivers)
- Survey validation: **≥ 30–50 responses** confirming the core blocker

### 2.3 Architecture Decisions (locked)
- **Monorepo** (pnpm) with `apps/api` (FastAPI) and `apps/web` (Next.js admin)
- **Auth:** RS256 against Google public certs; roles from `users.role` DB column, never token claims
- **Safety tier (v1):** `display_tier = "unverified"` when report count = 0; majority vote across reports; tie → more cautious tier. **No official override in v1.**
- **Pagination:** default 20, max 100, offset cap 100,000; response `{items, total, limit, offset}`
- **Errors:** consistent `{error: {code, message, details?}}`; validation details never include submitted values
- **Rate limiting:** per-IP on all writes (generous — Nigerian carrier NAT), per-user after auth
- **CORS:** explicit origin list; `*` rejected at startup; production requires https
- **ISR:** 5-minute revalidate on spot detail pages (safety-freshness tradeoff)
- **Map:** static map image first, interactive Mapbox GL on tap; bbox on `moveend` with 250ms debounce
- **Frontend status:** paused for redesign. Backend proceeds in parallel.

## 5. Migration 0005 — Reduced Scope (v1)

Because the Hybrid Model is deferred, Migration 0005 contains **only**:

```sql
-- 0005_saved_spots_and_booking_info.py

-- 1. Spots: booking handoff only (no official_safety_index)
ALTER TABLE spots
  ADD COLUMN booking_info JSONB NULL;

-- 2. Saved spots: favorites + optional scheduling fields
CREATE TABLE saved_spots (
  user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  spot_id UUID NOT NULL REFERENCES spots(id) ON DELETE CASCADE,
  planned_date DATE NULL,
  notes TEXT NULL,
  saved_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, spot_id)
);

CREATE INDEX idx_saved_spots_user_id ON saved_spots(user_id);
CREATE INDEX idx_saved_spots_planned_date ON saved_spots(user_id, planned_date)
  WHERE planned_date IS NOT NULL;
```

**Downgrade:** drop table; drop column. `alembic check` clean after up/down/up.

**Explicitly NOT in 0005:**
- `official_safety_index` — Phase 5+
- `display_tier` backfill — still needs the stored-vs-computed decision (§5.1 below)
- `safety_report_count` trigger — still needs the mechanism decision (§5.1)
- Itinerary API endpoints — must be added to §6.2 first if in scope

### 5.1 Open Decisions Before Writing 0005
1. **`planned_date` / `notes` in v1 or later?** If the itinerary scheduler is later, `saved_spots` can ship with just `(user_id, spot_id, saved_at)` and the two fields added in a later migration. Recommendation: **include them now** — they're nullable, zero cost, and avoid a second migration.
2. **`display_tier`: stored or computed?** v1 currently returns a computed `display_tier` from the service. If it's stored, 0005 needs a backfill + update mechanism. Recommendation: **keep computed**, remove from any stored-column assumption.
3. **`safety_report_count`: trigger vs. service-layer vs. computed?** Recommendation: **trigger on `safety_reports` insert/delete** (safety-critical field; drift is unacceptable).
4. **`safety_status` vs. `display_tier`:** two concepts or one? Recommendation: keep `display_tier` (computed safety tier) and treat any `safety_status` as the moderation state, renamed `moderation_status` if added.
5. **Itinerary endpoints in this deliverable?** If yes, add `GET/POST/PATCH/DELETE /api/itinerary/*` to §6.2 with request/response schemas. If no, `saved_spots` is storage only and the scheduler ships later.

### 5.2 `booking_info` — Strict Pydantic Schema (locked)
```python
class BookingInfo(BaseModel):
    model_config = ConfigDict(extra="forbid")
    is_bookable: bool
    booking_url: Optional[HttpUrl] = None
    whatsapp_contact: Optional[str] = Field(
        default=None, pattern=r"^\+?[1-9]\d{7,14}$"
    )

    @model_validator(mode="after")
    def require_contact_if_bookable(self):
        if self.is_bookable and not (self.booking_url or self.whatsapp_contact):
            raise ValueError("bookable spots require booking_url or whatsapp_contact")
        return self
```
**Handoff security decision (to add to this PRD before building the UI):** allow any `https://`, allowlist trusted domains, **or** show a "You're leaving Spotfinder to [domain]" interstitial. Recommendation: **interstitial** (middle ground, no maintenance burden).

## 10. Appendix

### 10.1 Database Schema (v1 target)
- **users:** id, phone, email, name, avatar, role, created_at
- **spots:** id, slug, name, description, category, state, city, coordinates (PostGIS), cost_estimate (JSONB), **booking_info (JSONB, 0005)**, safety_report_count, is_active, is_verified, rejection_reason (0004), created_by, created_at, updated_at. *(No `official_safety_index` in v1.)*
- **reviews:** id, spot_id, user_id, rating, safety_rating, comment, created_at
- **photos:** id, spot_id, user_id, url, is_approved, rejection_reason (0004), created_at
- **safety_reports:** id, spot_id, user_id, incident_type, severity_level, description, safe_hours_start/end, reported_at; unique `(spot_id, user_id)` (0003)
- **saved_spots (0005):** user_id, spot_id, planned_date, notes, saved_at; PK `(user_id, spot_id)`
